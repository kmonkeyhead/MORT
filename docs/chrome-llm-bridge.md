================================================================
크롬 로컬 번역기 - 크롬 내장 AI를 MORT의 번역기로 쓰기
================================================================

크롬에는 기기 안에서 도는 번역 모델과 LLM이 들어 있다. 번역 방식에서
"크롬 로컬 번역기"를 고르면 그 모델로 번역한다. API 키도 인터넷도 필요 없고
번역은 전부 사용자 PC 안에서 끝난다.

  MORT ──▶ 로컬 서버(MORT 안) ──WebSocket──▶ 크롬 브릿지 창
                                                  │
                                      Translator / LanguageModel API
                                                  │
  MORT ◀──────────────────────────────────────────┘

별도 실행 파일은 없다. 서버는 MORT 프로세스 안에서 돌고, MORT를 끄면 서버도 브릿지 창도
같이 닫힌다. 서버가 사라진 창은 아무것도 못 하고 재접속만 되풀이하므로 남겨 두지 않는다.
(제목으로 찾은 그 창에만 닫기를 보낸다. 크롬 프로세스를 죽이지 않으므로 보던 다른 탭은 그대로다.)


================================================================
1. 왜 크롬 창이 하나 떠 있어야 하는가
================================================================

크롬 내장 AI API에는 외부 프로그램이 그냥 부를 수 없게 만드는 제약이 둘 있다.

  · Web Worker에서 못 쓴다. 실제 문서(페이지)가 살아 있어야 한다.
  · 아직 내려받지 않은 모델은 create() 직전에 사용자 조작이 있어야 한다.
    이미 받아 둔 모델은 조작 없이 만들어진다. 5장을 보라.

그래서 MORT가 모델을 직접 부르는 구조는 성립하지 않고, 살아 있는 크롬 문서를
반드시 거쳐야 한다. 확장 프로그램으로 만들어도 이 제약은 그대로다.

브릿지 창을 닫으면 번역이 멈춘다. 버그가 아니라 위 제약의 결과다.


▶ WebView2를 MORT 안에 얹어 한 창으로 끝낼 수는 없나

  없다. 확인해 봤고 결론은 "모델이 없다"였다.

  WebView2 런타임 152.0.4191.62 에서 브릿지 페이지를 띄우고 확인한 결과 :

    LanguageModel                        → 객체 자체가 없음
    Translator                           → 객체는 있음
    Translator.availability(ja→ko)       → "unavailable"
    Translator.create(ja→ko)             → NotSupportedError:
                                           Unable to create translator for
                                           the given source and target language.

  API 표면만 Edge 쪽에 노출되어 있고 기기 내장 모델은 붙어 있지 않다.
  모델은 크롬에만 있으므로 크롬 창이 필요하다.


================================================================
2. 준비물
================================================================

  · 데스크톱용 크롬. 안드로이드·iOS는 안 된다.
  · Translator API             : 크롬 138 이상
  · Prompt API(LanguageModel)  : 크롬 148 이상

크롬의 내장 AI 모델은 구글이 갱신한다. Gemma 4 적용 여부도 크롬 쪽 버전과
플래그에 달린 문제이고, MORT는 어떤 모델이 붙어 있든 같은 JS API를 부르므로
코드를 고칠 필요가 없다.


================================================================
3. 쓰는 법
================================================================

  1) 번역 방식에서 "크롬 로컬 번역기"를 고르고 적용한다.
     → 이때는 크롬 창이 뜨지 않는다. 설정만 반영한다.
  2) 번역을 시작한다.
     → 이때 MORT가 로컬 서버를 열고 크롬 창을 띄운다.
     → 크롬 창은 열리자마자 스스로 연결하고 모델 준비까지 시도한다.
     → 번역 패널이 "브릿지 활성화 됨"으로 바뀌면 끝이다. 누를 것이 없다.

번역 패널의 안내 문구는 크롬이 설치되어 있어야 한다는 것 하나뿐이다.

창이 뜨는 시점을 "적용"이 아니라 "번역 시작"으로 둔 이유는, 설정만 만지는 동안
브라우저가 튀어나오면 성가시기 때문이다.

쓸 모델을 이미 받아 둔 상태라면 여기까지 클릭이 한 번도 필요 없다.
안 받은 모델이 있으면 크롬 창이 "받으시겠습니까?"라고 물어본다. 5장을 보라.

크롬 창을 닫았거나 다시 열고 싶으면 번역 패널의 [설정 열기]를 누른다.
엔진 선택과 모델 준비는 전부 그 크롬 창 안에 있다.

원문/결과 언어는 MORT에서 고른 값을 그대로 쓴다. 크롬 창에는 언어를 고르는 곳이 없다.

  번역 탭 > "번역 언어"
    [ 중국어 번체 ] 에서  ->  [ 한국어 ] 로 번역

번역기마다 언어를 따로 고르던 칸은 하나로 합쳤다. 여기서 바꾸고 적용하면 크롬 로컬 번역기에도
바로 반영된다. 번역기별 코드 변환은 TranslateLanguageService가 하고, 크롬 브릿지는 거기서
받은 구글 코드(zh-TW, pt-BR 등)를 크롬이 아는 형태(zh-Hant, pt)로 한 번 더 바꿔 넘긴다.

MORT는 크롬 창이 붙을 때와 설정을 적용할 때 이 언어 설정을 창에 알려 준다. 그래서 첫
번역 전에도 크롬 창이 맞는 언어 쌍으로 모델을 준비하고 상태도 그 기준으로 보여 준다.
이걸 안 보내면 창은 첫 번역이 올 때까지 어떤 쌍을 쓸지 몰라, 시험 칸 기본값(ja→ko)을
기준으로 삼아 엉뚱한 모델을 받고 엉뚱한 상태를 보여 준다.

크롬 창 아래쪽 "직접 시험해 보기"의 언어 선택은 그 칸에서 손으로 시험할 때만 쓰는 것이고
MORT 번역에는 영향이 없다.

크롬 창 자체의 표시 언어(한국어 / 영어)는 창 오른쪽 위 [KR] [EN] 버튼으로 바꾼다.
처음에는 MORT의 UI 언어를 따르고(주소의 ?lang=ko|en), 버튼으로 고르면 그 값을 크롬
localStorage 에 두고 다음부터 그쪽을 쓴다. 바꿀 때 페이지를 새로 고치지 않고 문구만 갈아 끼운다.
새로 고치면 WebSocket이 끊겨 그 사이 번역 요청이 실패하고 진행 중인 모델 준비와 번역 기록도 사라진다.
이미 적힌 로그와 번역 기록 줄은 적을 때의 언어로 남는다.


================================================================
4. 엔진 - 이게 이 번역기에서 제일 중요한 선택이다
================================================================

크롬 내장 AI에는 성격이 다른 두 경로가 있고, 한국어 사용자에게는 차이가 크다.

  translator : Translator API. 번역 전용 모델.
               ko, ja, zh, en 등 38개 언어를 지원한다.
               빠르고 결과가 안정적이다.

  llm        : LanguageModel(Prompt API). 이른바 로컬 LLM.
               문맥을 보고 번역하지만 ▶ 공식 지원 언어가
               en / ja / es / de / fr 뿐이다. 한국어는 아직 목록에 없다.
               한국어로 뽑아도 품질이 보장되지 않는다.

  auto       : 언어 쌍을 Translator가 지원하면 Translator를 쓰고,
               아니면 LLM으로 넘긴다. 기본값.

auto가 한 번 정한 경로는 언어 쌍별로 기억해 두고 다음 번역부터 그대로 쓴다. 번역마다
없는 모델을 다시 찾으면 그만큼 느려지고 로그도 같은 말로 채워진다. 기억은 창이 살아
있는 동안만 유지되고, 새로 고치면 처음부터 다시 판단한다. 엔진을 직접 고른 경우는
기억하지 않는다. 그건 이미 고정된 선택이라 기억할 것이 없다.

그 쌍의 모델을 나중에 받으면 기억은 풀린다. 받아 놓고도 계속 LLM을 쓰면 안 되기 때문이다.

일본어 게임을 한국어로 보는 보통의 MORT 사용이라면 auto(사실상 Translator)가
맞다. LLM 경로는 en/ja 결과가 필요하거나 문맥 번역을 시험해 볼 때 쓴다.

실제 확인한 결과 :

  新しいゲームを始めますか？ / 設定を保存しました。
    → 새로운 게임을 시작하시겠습니까? 설정을 저장했습니다.   (translator)

  魔王を倒すには、まず村の長老に話しかけてください。
    → 마왕을 물리치려면 먼저 마을 장로와 대화하십시오.       (translator)

  Save the game before you leave.
    → 게임 히어로를 떠나기 전에 저장하세요.                  (llm)

세 번째가 LLM 경로의 한국어 품질 문제다. "the game"을 "게임 히어로"로 옮겼다.

Translator는 줄바꿈을 공백으로 합친다. OCR 블록 단위로 번역하는 MORT 구조에서는
문제되지 않지만 알아 둘 만하다.


================================================================
5. 모델 내려받기
================================================================

사용자 조작이 필요한 범위를 크롬이 정확히 알려 준다. create() 를 조작 없이
불렀을 때 크로미움이 돌려주는 문구는 이렇다.

  Requires a user gesture when availability is "downloading" or "downloadable".

즉 조작이 필요한 건 ▶ 아직 내려받지 않은 모델뿐이다. 이미 받아 둔 모델은
조작 없이 그냥 만들어진다. (MDN에는 "create()는 항상 사용자 조작이 필요하다"고
적혀 있지만 실제 구현은 위와 같다. 문서보다 구현이 느슨한 쪽이다.)

그래서 브릿지 페이지는 열리자마자 다음을 한다.

  1) WebSocket 연결      - 조작 필요 없음. MORT는 창이 열리자마자 브릿지를 본다.
  2) availability() 확인 - 조작 필요 없음.
  3) create() 시도       - 이미 받은 모델이면 그대로 성공한다.
                           내려받아야 하면 여기서만 거부당한다.

3번이 거부당하면 크롬 창에 대화상자가 뜬다.

  ┌────────────────────────────────────────────────┐
  │ 번역 모델이 없습니다                            │
  │ 해당 번역 모델(ru → ko)을 받아야 합니다.        │
  │ 받으시겠습니까?                                 │
  │ 번역 모델이 없을 경우 LLM으로 처리됩니다.       │
  │                            [나중에]  [받기]     │
  └────────────────────────────────────────────────┘

이 대화상자는 반드시 크롬 창 안에 있어야 한다. MORT 쪽에서 띄우면 그 확인 클릭은
크롬의 사용자 조작으로 인정되지 않아서 내려받기가 시작되지 않는다.
같은 이유로 MORT가 대신 눌러 줄 수도 없다.

문구는 두 줄로 나눈다. 무엇을 받아야 하는지가 첫 줄, 받지 않으면 어떻게 되는지가 둘째 줄이다.
한 문장에 다 넣으면 길어져서 정작 눌러야 할 버튼이 눈에 안 들어온다.
언어 쌍(ru → ko)은 남긴다. "해당 번역 모델"이 무엇인지 모르면 받아도 맞는 것을 받았는지 알 수 없다.

▶ 무엇을 받는가 - 받기는 한 종류만 받는다

  LLM은 부가 기능이라 사용자가 LLM을 직접 고른 경우에만 받겠느냐고 묻는다.
  auto에서 4GB를 받으라고 들이밀면, 언어팩(76MB)만 받으면 될 사람까지 큰 내려받기로 끌고 간다.

  [받기]가 실제로 받는 것은 대화상자가 말한 그 하나다.

    엔진 llm          → LLM 모델
    엔진 translator   → 번역 언어팩
    auto + 언어팩 없음 → 번역 언어팩만. LLM은 [LLM 모델 받기]로 따로 받는다
    auto + LLM만 없음  → 받을 것이 없다. 번역은 언어팩으로 되므로 [확인]만 띄운다
    지원하지 않는 쌍   → 받을 것이 없다. 그 쌍은 언어팩 자체가 없다

  문구와 실제로 받는 것이 어긋나면 사용자는 받았다고 생각하는데 아무것도 안 받힌 상태가 된다.
  실제로 그런 적이 있다. auto에서 "LLM 모델을 받아야 합니다"라고 띄워 놓고 [받기]를 누르면
  이미 있는 언어팩만 만지고 "모델을 준비했습니다" 로그를 남겼다. 그래서 대화상자가
  받을 대상(translator / llm / none)까지 들고 다니게 하고, 받기는 그 값만 본다.

  auto 모드에서는 번역 모델과 LLM을 모두 확인한 뒤에 알린다. 어느 쪽이 없는지에 따라
  둘째 줄이 달라지므로, 받지 않았을 때 무슨 일이 생기는지가 바로 보인다.

    · 번역 모델만 없음 : "번역 모델이 없을 경우 LLM으로 처리됩니다."
    · 둘 다 없음       : "LLM 모델도 없어 지금은 번역되지 않습니다. LLM은 부가 기능이라
                         [LLM 모델 받기]로 따로 받습니다."


▶ 모델 상태는 둘을 따로 보여 준다

  창 위쪽에 두 칸이 있다.

    ● 번역 모델 : 있음 (ru → ko)
    ● LLM 모델 : 없음 (부가 기능 · 4GB)

  예전에는 "모델 준비됨 / 모델 필요" 칸이 하나 더 있었는데 없앴다. 모델은 둘인데 상태 칸이 하나라
  어느 쪽 이야기인지 알 수 없었다. LLM은 있고 번역 모델만 없는 흔한 상태에서 "모델 필요"라고만 떠서,
  번역이 LLM으로 되고 있는데도 무언가 잘못된 것처럼 보였다. 받는 중·준비 실패 같은 상태도
  해당하는 모델 칸에 적는다.

  하나로 뭉뚱그리면 "모델 준비됨"이 어느 쪽을 말하는지 알 수 없고, 번역이 왜 LLM으로
  떨어졌는지도 설명되지 않는다. 번역 모델은 언어 쌍마다 다르므로 지금 보고 있는 쌍을 같이 적는다.
  그 쌍을 아예 지원하지 않으면 "없음"이 아니라 "이 언어 쌍은 언어팩이 없습니다"로 적는다.
  받아도 안 되는 것과 받으면 되는 것은 다른 이야기다.

이때 MORT는 ▶ 번역을 멈추고, 브릿지 창을 앞으로 꺼낸다. MORT 쪽에는 팝업을 두지 않는다.

묻는 창은 하나여야 한다. MORT에서 한 번, 브릿지에서 또 한 번 확인을 누르게 되는데
정작 받기 버튼은 브릿지에만 있어서 MORT 팝업은 지나가는 관문 노릇밖에 못 했다.
브릿지가 보낸 사유는 MORT 로그에 남는다. 번역 패널도 "모델이 없습니다"로 바뀐다.

멈추는 이유는, 멈추지 않으면 auto 모드가 조용히 LLM으로 떨어져 품질이 나쁜 결과가
계속 쌓이는데 사용자는 왜 그런지 알 수 없기 때문이다.

브릿지 창을 앞으로 꺼낼 때는 예약된 최소화도 같이 취소한다. 물어볼 일은 창이 뜬 직후에
생기는데, 그때 예약된 최소화가 그대로 걸리면 눌러야 할 대화상자를 작업 표시줄로 내려 버린다.
이 경합은 실제로 난다.

같은 것은 두 번 묻지 않는다. 창이 열릴 때 한 번 묻고 첫 번역 요청에서 또 묻는 일이 있었다.
[나중에]는 "지금은 됐다"는 뜻이므로 그 뒤로도 묻지 않는다. 받을 대상과 언어 쌍을 묶어
기억해 두고, 모델이 준비되거나 언어 쌍이 바뀌면 그 기억을 지워 다시 물을 수 있게 한다.

Translator가 아예 지원하지 않는 언어 쌍은 여기 해당하지 않는다. 그건 받아도 안 되므로
LLM으로 넘어가는 것이 정상 경로이고 멈추지 않는다.

[나중에]를 눌렀거나 미리 받아 두고 싶으면 크롬 창의 직접 받기 버튼을 쓴다.

  · [번역 언어 쌍 받기] : MORT가 실제로 요청한 언어 쌍을 받는다.
                          아직 요청이 없었으면 시험 칸에서 고른 쌍을 받는다.
  · [LLM 모델 받기]     : LLM 모델을 받는다. 용량이 크다.

받아야 할 쌍은 MORT가 보낸 값을 기준으로 잡는다. 시험 칸 선택을 기준으로 잡으면
정작 필요한 쌍은 계속 없는 채로 남아 매번 LLM으로 떨어진다.


▶ 지금 어떤 모델을 쓰는지

  크롬 창의 "받아 둔 모델" 줄에 나온다. 예 :

    LLM : v3Nano (2025.06.30.1229, 4.0 GB)
    번역 언어팩 : en_ja 75.9 MB, en_ko 75.4 MB, en_zh 76.6 MB

  v3Nano 는 Gemini Nano 3세대다. 어떤 모델이 붙는지는 크롬이 정하고, MORT는 고르지 않는다.
  JS API에는 모델 이름을 알려 주는 값이 없어서(LanguageModel.params() 는 topK/temperature만 준다)
  MORT가 크롬의 사용자 데이터 폴더에서 manifest.json 을 읽어 페이지에 넘겨 준다.

    OptGuideOnDeviceModel\<버전>\manifest.json 의 BaseModelSpec.name  ← LLM 모델 이름
    TranslateKit\models\<언어팩>\<버전>\                              ← 번역 언어팩

  크롬을 기본 경로가 아닌 곳에 설치했으면 못 찾는다. 그때는 "찾지 못했습니다"로 표시되고,
  번역 자체에는 영향이 없다.

  모델을 받은 뒤에는 목록이 자동으로 갱신된다. 직접 갱신하려면 [목록 새로 고침]을 누른다.


▶ 언어팩은 영어를 축으로 되어 있다

  Translator 언어팩은 언어 쌍마다 하나씩이 아니라 영어와의 쌍으로 저장된다.

    %LOCALAPPDATA%\Google\Chrome\User Data\TranslateKit\models\
        en_ja\...\en_ja_nmt, ja_en_nmt
        en_ko\...\en_ko_nmt, ko_en_nmt

  ja → ko 처럼 영어가 끼지 않은 쌍은 en_ja 와 en_ko 를 함께 써서 영어를 거쳐 옮긴다.
  그래서 한 쌍을 준비하면 팩이 두 개 받아질 수 있다. zh → ko 를 쓰려면 중국어 팩이
  따로 있어야 하고, 없으면 받아야 한다.


▶ 이미 받아 둔 모델은 그냥 쓴다

  이 창에서 준비 버튼을 누른 적이 없어도, 크롬이 이미 받아 둔 언어 쌍이면
  availability가 available을 주고 그때는 사용자 조작 없이 create() 가 된다.
  그래서 번역 요청이 오면 먼저 availability를 확인하고, available이면 바로 만들어 쓴다.

  이걸 확인하지 않고 "이 창에서 준비한 적 없음 = 모델 없음"으로 처리하면,
  멀쩡히 있는 모델을 두고 매번 LLM으로 떨어진다. 그러면 엔진을 바꿔도 결과가
  달라지지 않아서 설정이 동작하지 않는 것처럼 보인다.


▶ 로그를 어디서 보나

  두 군데에 남는다.

  · 크롬 창 아래 [로그]  — 이 창에서 일어난 일 전부
  · MORT 로그           — 그중 경고와 오류만

  브릿지 창은 평소 최소화되어 있다. 창을 열어 봐야만 알 수 있게 두면 로그를 남기는 뜻이 없어서,
  경고(노랑)와 오류(빨강)는 언제나 MORT 로그로 넘어간다. MORT 로그에서는 이렇게 보인다.

    [ChromeBridge][page] [경고] Translator 경로 실패 → LLM으로 넘깁니다 (ja>hu) : …
    [ChromeBridge][page] [오류] 번역 실패 (ja → hu) : 번역 모델(ja>hu)을 아직 내려받지 않았습니다.

  [자세히]를 켜면 요청 도착, 원문 언어 감지와 확신도, 경로 선택, 걸린 시간까지 남는다.
  평소에 남기지 않는 이유는 요청 하나가 로그 대여섯 줄을 차지해서 정작 봐야 할 경고가 묻히기 때문이다.
  로그는 400줄에서 끊는다. [복사]는 로그 전체를 클립보드에 넣는다.

  MORT 쪽에서도 두 가지를 더 적는다.

    [ChromeBridge] 번역 응답 없음 : ja → ko / auto / 42자 / 30초 초과
    [ChromeBridge] 창이 연결되어 있지 않아 번역 요청을 처리하지 못했습니다. …

  연결 없음은 끊긴 뒤 첫 요청에만 적는다. OCR 회차마다 적으면 로그가 그 말로만 찬다.


▶ 번역 기록에 무엇이 적히나

  크롬 창의 [번역 기록]은 줄마다 이렇게 남는다.

    12:44:20  [LLM] [재시도 성공]  ja → ko · 감지 ja 98% · 842ms · 15자
    MORT 요청 : 자동 · Translator 실패로 LLM에 넘겼습니다 : … · 다시 시켜서 고쳤습니다
    村の入口で待っていてください。
    마을 입구에서 기다려 주세요.

  경로 배지만으로는 "왜 이 문장만 이상한가"에 답할 수 없다. 그 아래 한 줄이 그 답이다.
  MORT가 시킨 것인지 이 창에서 고른 것인지, 언어팩으로 번역했는지 Translator가 실패해 넘어왔는지,
  auto가 앞서 이 쌍을 LLM으로 정해 둔 것인지가 적힌다.

  [재시도 성공]은 LLM이 목표 언어로 답하지 않아 다시 시켜 고쳐진 경우,
  [번역 안 됨]은 두 번 다 실패해 원문을 그대로 넘긴 경우다.


▶ LLM이 목표 언어를 무시하고 원문을 그대로 돌려주는 일

  실제로 일어난다. ja → ko 로 보냈는데 일본어가 그대로 돌아온다.
  Translator 모델은 언어 쌍이 모델 자체에 박혀 있어 이런 일이 없지만, LLM은 지시를 따르는 것뿐이라
  언어 쌍을 자료로 읽어 버리면 원문을 옮겨 적고 만다. 작은 모델일수록 자주 그런다.

  같은 문장("村の入口で待っていてください。")을 반복해 측정한 결과 :

    고치기 전 : 한국어로 나온 것 1 / 5
    고친 뒤   : 12 / 12 (다른 문장 섞어 10회 더 돌렸을 때도 재시도가 걸리지 않았다)

  세 가지를 걸었다.

  1. 언어 쌍을 세션에 박는다
     LanguageModel.create 에 expectedInputs / expectedOutputs 로 쓰는 언어를 알려 주고,
     시스템 프롬프트에도 "너는 한국어로만 답한다"를 넣는다. 프롬프트 문장보다 이쪽이 강하게 먹는다.
     크롬 빌드나 언어에 따라 힌트가 거부당할 수 있어서, 막히면 힌트 없이 다시 만든다.

     목표가 한국어면 이 크롬은 실제로 거부한다.

       The requested language options are not supported.

     Prompt API의 공식 지원 출력 언어가 en/ja/es/de/fr 이기 때문이다. 그래서 한국어에서는
     아래 2·3번이 실제로 일한다. 힌트는 일본어나 영어를 목표로 삼을 때 쓰인다.
     거부당하는 것이 정상이라 경고로 올리지 않고 [자세히] 로그에만 남긴다.
     언어 쌍이 바뀌면 세션을 버리고 새로 만든다. 시스템 프롬프트에 쌍이 박혀 있기 때문이다.

  2. 원문 뒤에서 한 번 더 말한다
     지시를 원문 앞에만 적으면 모델이 그걸 잊는다. 작은 모델은 마지막에 읽은 문장을 가장 강하게 따른다.

  3. 결과를 글자로 검사하고 한 번 다시 시킨다
     목표 언어 글자보다 원문 글자가 많으면 번역이 덜 된 것으로 본다.
     원문을 통째로 되돌려 준 것뿐 아니라 "공격力が上がった!" 처럼 반만 바꾼 것도 여기서 걸린다.
     고유명사를 원문 그대로 남기는 건 정상이라("미사키(ミサキ)의 검") 목표 언어 글자가 더 많으면 넘어간다.

     재시도는 이력이 없는 새 복제본에 묻는다. 방금 그 답이 남아 있는 세션에 다시 물으면
     모델이 자기 답을 그대로 되풀이하는 것을 실제로 봤다(두 번 다 같은 원문).

     두 번 다 실패하면 원문을 그대로 넘기고 MORT 로그에 남긴다. 오류로 만들지 않는 이유는,
     화면에 오류 문구가 뜨는 것보다 원문이 보이는 편이 낫기 때문이다.

  판정하지 않는 조합이 있다. 같은 글자를 쓰는 언어끼리(영어 → 프랑스어), 표에 없는 언어,
  그리고 중국어 → 일본어. 한자로만 이뤄진 일본어 문장은 중국어와 글자가 같아서 가릴 방법이 없다.
  잘못 판정해 멀쩡한 번역을 버리는 쪽이 더 나쁘다.

  Translator 언어팩이 있는 쌍은 애초에 이 경로로 오지 않는다. 이건 팩이 없는 쌍의 이야기다.
  같은 증상이 자주 보이면 그 언어팩을 받는 것이 가장 확실하다.


▶ 받아 둔 모델을 지우려면

  크롬 창의 [모델 관리 / 지우기] 버튼을 누른다. 두 모델은 지우는 곳이 아예 다르므로
  한 덩어리로 적지 않고 나눠서 보여 준다. 한 덩어리로 두면 어느 설명이 어느 모델 것인지
  읽어 내야 해서, 지우러 왔다가 무엇을 눌러야 할지 모르고 닫게 된다.

    ┌────────────────────────────────────────────────────────┐
    │ 모델 관리 / 지우기                                      │
    │ 두 모델은 지우는 곳이 다릅니다.                          │
    │ ┌────────────────────────────────────────────────────┐ │
    │ │ ① 번역 언어팩 — en_ja 75.9 MB, en_ko 75.4 MB       │ │
    │ │   chrome://on-device-translation-internals/        │ │
    │ │   실제 폴더 : …\User Data\TranslateKit\models      │ │
    │ └────────────────────────────────────────────────────┘ │
    │ ┌────────────────────────────────────────────────────┐ │
    │ │ ② LLM 모델 — v3Nano 4.0 GB                         │ │
    │ │   크롬 설정 > 시스템 > 기기 내 AI 를 끄면 지워집니다 │ │
    │ │   …\User Data\OptGuideOnDeviceModel\2025.8.8.1141  │ │
    │ └────────────────────────────────────────────────────┘ │
    └────────────────────────────────────────────────────────┘

  언어팩은 chrome://on-device-translation-internals/ 에서 설치·제거한다. 주소는 클립보드에
  복사하고 화면에도 띄운다. 새 탭 주소창에 붙여 넣으면 된다.

  LLM 모델(4GB)은 그 페이지가 아니라 크롬 설정에서 지운다.
  설정 > 시스템 > 기기 내 AI 를 끄면 크롬이 모델 파일을 지우고,
  꺼 둔 동안에는 다시 받지도 않는다.

  모델이 실제로 있는 폴더도 같이 적는다. 크롬 설정에는 그 위치가 안 적혀 있어서, 용량을
  확인하거나 정말 지워졌는지 보려면 폴더를 찾아가야 한다. 경로는 페이지가 알 수 없고
  (웹페이지라 파일을 못 본다) MORT가 읽어 models 메시지로 넘겨 준다.

  MORT가 직접 지우지 않는 이유는 셋이다.
    · JS API에 삭제 기능이 없다. destroy() 는 메모리 세션만 해제한다.
    · 파일을 직접 지우는 것은 구글이 권장하지 않고, 크롬이 실행 중이면
      잠겨 있으며, 컴포넌트 업데이터가 다시 받는다.
    · 사용자의 브라우저 설치를 번역기가 건드릴 일이 아니다.

  chrome:// 주소는 웹페이지가 직접 열 수도, 링크로 걸 수도 없다. 주소창에 붙여 넣는
  방법뿐이라 복사와 안내로 처리한다. 클립보드가 막힌 환경에서도 주소를 화면에 그대로
  띄우므로 눈으로 읽고 칠 수 있다.

모델 준비는 오래 걸리고 실패하기도 하지만 그동안에도 MORT와의 연결은 유지된다.
연결부터 맺고 준비는 뒤에서 진행하기 때문이다.

6. 설정
================================================================

선호하는 엔진은 고급 설정 > 번역 설정 > "크롬 로컬 번역기"에서 고른다.

  선호하는 엔진   자동 / LLM / Translator API. 기본 자동

적용을 누르면 번역 설정을 다시 적용하지 않아도 열려 있는 크롬 창에 바로 알린다.
나머지는 고급 설정 파일에만 있다. 기본값으로 그냥 쓰면 된다.

  @CHROME_BRIDGE_PORT      로컬 서버 포트. 기본 16899
  @CHROME_BRIDGE_MODE      엔진 기본값. auto / translator / llm. 기본 auto
                           (위 "선호하는 엔진"이 이 값을 읽고 쓴다)
  @CHROME_BRIDGE_AUTO_RUN  번역 시작할 때 크롬 창 자동 열기. 기본 true
  @CHROME_BRIDGE_TIMEOUT   한 건 최대 대기 시간(초). 기본 30

MORT가 mode 값을 같이 보내므로 기본값은 이 설정을 따른다. 다만 크롬 창의 엔진을
직접 고르면 그때부터는 그 선택이 우선한다. 그러지 않으면 창에서 엔진을 바꿔도
아무 일도 일어나지 않아 설정이 동작하지 않는 것처럼 보인다.


================================================================
7. 로컬 서버 (커스텀 API로 붙이거나 확인할 때)
================================================================

크롬 로컬 번역기가 켜져 있는 동안 로컬 서버가 함께 떠 있다.

  GET  /           브릿지 페이지
  GET  /status     연결 상태 (JSON)
  GET  /ws         브릿지 페이지가 붙는 WebSocket
  POST /translate  번역 요청

MORT 자신은 이 HTTP를 거치지 않고 서버 안의 허브를 바로 부른다.
/translate 는 커스텀 API 프리셋으로 붙이거나 손으로 확인할 때 쓰는 통로다.

  요청  { "text": "원문", "source": "ja", "target": "ko", "mode": "auto" }
  성공  { "result": "번역 결과", "engine": "translator" }
  실패  { "error": "사람이 읽을 수 있는 실패 사유" }   (HTTP 503 / 400)

서버는 127.0.0.1 에만 바인딩한다. 외부에서는 접근할 수 없다.


================================================================
8. 알아 둘 점
================================================================

  · 크롬 창을 닫거나 다른 주소로 이동하면 번역이 멈춘다.
    번역 패널의 [설정 열기]로 다시 연다. 연결이 끊기면 3초마다 다시 붙는다.

  · 크롬 창의 X 버튼은 MORT가 가로챌 수 없다. 그 창의 주인은 크롬이지 MORT가 아니다.
    닫으면 번역이 멈추고, 번역 패널의 [설정 열기]로 다시 열어야 한다.
    평소에는 최소화되어 있으므로 실수로 닫을 일은 드물다.

  · 브릿지 창은 항상 하나만 유지한다. 세 겹으로 막는다.

      1) 이미 붙어 있으면 새로 띄우지 않는다.
      2) 방금 띄웠는데 아직 안 붙었으면 12초 동안 기다린다.
         번역 시작과 [설정 열기]가 겹칠 때 창이 두 개가 되는 걸 막는다.
      3) 그래도 두 번째 창이 붙으면 먼저 있던 창이 자리를 내주고 스스로 닫힌다.
         죽은 창이 화면에 남아 있으면 어느 창이 살아 있는지 알 수 없기 때문이다.

  · 브릿지 창은 기본적으로 최소화되어 있다. 사람이 볼 일이 거의 없는 창이다.

      - 번역 시작 때 새로 뜰 때 : 띄우자마자 최소화한다.
      - [설정 열기]로 부른 경우 : 펼쳐서 앞으로 꺼낸다.
      - 모델 없음 알림에서 확인 : 펼쳐서 앞으로 꺼낸다. 받기 버튼이 거기에만 있다.

    번역을 시작할 때마다 창이 앞에 뜨면 게임에서 포커스를 빼앗고, 전체 화면 게임이면
    그것만으로 창 모드로 튕기기도 한다.

    최소화해도 번역은 그대로 된다. 실측값은 이렇다.

      보이는 상태     96ms   (첫 요청, 모델 로드 포함)
      최소화 +3초      4ms
      최소화 +63초     4ms
      최소화 +3분      5ms

    크롬의 백그라운드 지연은 타이머를 늦추는 것이고, 번역은 WebSocket 수신으로 깨어나
    네이티브 호출을 하므로 해당되지 않는다.

    완전히 숨기지는(작업 표시줄에서도 사라지게) 않는다. 그렇게 하면 MORT가 비정상 종료했을 때
    사용자가 그 창을 찾아 닫을 길이 없다. 최소화는 작업 표시줄에 남아 되찾을 수 있다.

  · 창을 닫은 뒤에는 번역해도 다시 뜨지 않는다. 닫은 것은 사용자의 뜻으로 본다.
    번역할 때마다 다시 띄우면 게임 위로 창이 계속 올라온다.
    다시 쓰려면 번역 패널의 [설정 열기]를 누른다.

  · Translator.availability() 가 응답하지 않는 크롬 빌드가 실제로 있다.
    모델을 건드리는 호출에는 전부 제한 시간을 걸어 두었으므로, 그런 경우
    확인을 건너뛰고 진행하거나 사유를 남기고 실패한다. 번역 줄 전체가
    멈추는 일은 없다.

  · 번역 요청은 크롬 창 안에서 한 건씩 차례로 처리한다.
    OCR이 빠르게 반복되어도 요청이 서로 섞이지 않는다.

  · 오버레이처럼 OCR 영역이 여럿이면 영역마다 따로 번역해서 보낸다.
    MORT는 원래 영역들을 구분 토큰("//////")으로 이어 붙여 한 번에 넘기고 결과를
    같은 토큰으로 다시 쪼개는데, 크롬 내장 AI는 그 토큰을 지켜 주지 않는다.
    Translator는 줄바꿈을 공백으로 합쳐 "//////\n"을 "////// "로 만들고,
    LLM은 마커째 지우기도 한다. 그대로 두면 분리가 안 되어 첫 영역에 전부 몰린다.
    그래서 ChromeBridgeTranslateAPI가 토큰으로 쪼개 한 덩이씩 번역한 뒤 같은 모양으로
    다시 잇는다. 덩이마다 왕복이 생기지만 영역이 정확히 나뉘고, 덩이별로 번역하므로
    구분 마커가 모델 입력에 섞이지 않아 결과도 더 깨끗하다.

  · 크롬 창의 "번역 기록"에 원문과 결과가 남는다. 새 것이 위로 쌓이고 50건까지 둔다.
    각 줄에는 어느 경로로 번역했는지가 색 배지로 붙는다.

      번역 모델 (초록)  Translator API. 번역 전용 모델.
      LLM      (노랑)  LanguageModel. 한국어 품질이 보장되지 않는 경로다.
      같은 언어         원문과 결과 언어가 같아 번역하지 않고 넘겼다.
      실패     (빨강)  결과 자리에 실패 사유가 그대로 들어간다.

    결과가 이상할 때 이 배지부터 본다. 노란 LLM 배지가 달려 있으면 Translator가
    그 언어 쌍을 처리하지 못해 넘어간 것이고, 4장의 품질 문제가 그대로 나타난다.


================================================================
9. 문제가 생기면
================================================================

  상태 : 번역을 시작하면 연결합니다
      아직 로컬 서버가 안 떴다. 번역을 시작하거나 [설정 열기]를 누른다.

  상태 : 초기화 대기중
      서버는 떴고 크롬 창이 아직 안 붙었다.

  상태 : 브릿지 활성화 됨
      크롬 창이 붙었고 쓸 모델도 있다. 번역할 수 있는 상태다.

  "크롬 브릿지 창이 연결되어 있지 않습니다"
      크롬 창이 닫혔다. 번역 패널의 [설정 열기]로 다시 연다.

  "번역 모델(ja>ko)을 아직 내려받지 않았습니다"
      5장대로 크롬 창에서 해당 언어 쌍을 준비한다.

  "크롬 브릿지가 30초 안에 응답하지 않았습니다"
      모델을 내려받는 중이거나 창이 늦춰진 상태다. 창을 앞으로 꺼내고
      크롬 창 아래쪽 로그에서 진행 상황을 본다.

  "이 브라우저에는 내장 AI API가 없습니다"
      크롬이 아니거나 버전이 낮다. 2장의 버전 조건을 확인한다.

  포트를 열지 못했다는 로그
      다른 프로그램이 16899를 쓰고 있다. @CHROME_BRIDGE_PORT 를 바꾼다.

사유는 두 군데에 남는다. MORT 로그에는 서버가 본 것이, 크롬 창 아래쪽
로그에는 모델이 본 것이 남는다. 두 로그를 같이 보면 어느 쪽에서 끊겼는지 갈린다.
